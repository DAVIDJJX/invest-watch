# InvestWatch — 個人理財監控儀表板

每天自動抓黃金、台股、美股、原油、比特幣與匯率的公開行情，算成幾個看得懂的指標，
放在一個手機和電腦都能開的網頁上。

**網址**：https://davidjjx.github.io/invest-watch/

---

## ⚠ 先講清楚兩件事

**一、這裡沒有任何投資建議。**
網站上的「相對低檔區／中性／相對高檔區」燈號，只是把 RSI、均線位置、52 週區間百分位
這些客觀數字做分類。這些規則**沒有經過任何歷史回測驗證**，不構成投資建議，也不保證
未來走勢。實際投資決定與盈虧由使用者自行負責。

**二、這個公開倉庫裡沒有任何個人資料。**
這裡只有公開的市場價格。持倉、成本、進場紀錄等個人資料一律不進這個倉庫
（Phase 3 會存在瀏覽器本機或使用者自己的私人倉庫）。

---

## 它是怎麼運作的

```
GitHub Actions（雲端定時工讀生）
  每天台北時間 10:00 / 13:00 / 15:00
      │
      ├─ 跑 scripts/fetch_data.py 去各官方網站抓牌價
      ├─ 更新 data/latest.json（最新報價）與 data/history/*.json（日線歷史）
      └─ 自動 commit + push 回這個倉庫
                                    │
                                    ▼
                       GitHub Pages 把倉庫變成網站
                       你用手機或電腦開網址就看得到
```

重點：**更新完全不需要你的電腦開機**，全部在 GitHub 的主機上跑。

前端不會直接連台銀／證交所——那些網站擋跨網域請求（CORS），所以一律由 Actions 上的
Python 先抓好存成 JSON，網頁只讀自家倉庫的靜態檔。

## 自己動手跑

```bash
# 安裝套件（只需要一次）
pip install requests

# 抓一次資料。--source 與 --slot 都是必填的：
#   --source  cloud = 雲端負責的標的、local = 家用電腦負責的台銀黃金（誰負責哪幾項看 data/assets.json 的 owner）
#             各自只寫自己的 data/sources/<source>.json，不會碰到對方的
#   --slot    時段標籤，由呼叫者告知、程式不猜。本機只能用 light（本機不產報告）；
#             雲端由 cron-job.org 告知 morning / midmorning / close / review / manual
python scripts/fetch_data.py --source cloud --slot manual
python scripts/fetch_data.py --source local --slot light

# 把兩邊的分片合成前端要看的 data/latest.json
python scripts/merge_latest.py

# 產生這個時段的報告（要先跑過上面的合併）。manual 寫到 report-manual.json，
# 不會動首頁讀的 report-latest.json
python scripts/report.py --slot manual

# 盤中輕量更新（只更新現價，不重抓歷史）
python scripts/fetch_data.py --source local --slot light --light

# 只抓其中幾項（測試用，同一個 owner 底下沒選到的會沿用上次結果）
python scripts/fetch_data.py --source local --slot light --only gold_twd,gold_cny

# 跑測試
python -m unittest discover -s scripts -p "test_*.py"
python scripts/test_race_recovery.py     # 競態實測，不會碰到 GitHub

# 本機開網站看看
python -m http.server 8765
# 然後瀏覽器開 http://localhost:8765
```

想手動觸發雲端更新：GitHub 倉庫 → **Actions** 分頁 → 左邊選「更新市場資料」→
右邊 **Run workflow** → 按綠色按鈕。

## ⚠ 已知限制：台銀資料在雲端抓不到

2026-08-31 實測發現：**臺灣銀行的網站會擋掉 GitHub Actions 的連線**。

台銀用了機器人防護（Akamai），對「資料中心 IP」特別嚴格。GitHub Actions 的主機
就在資料中心裡，實測每個網址連試 8 次全部只拿到驗證頁；同一支程式在家用電腦上跑
卻一次就過。

直接抓台銀的原本有 5 項：黃金存摺 TWD、黃金存摺 CNY、實體黃金條塊、美元/台幣、人民幣/台幣。
**匯率那 2 項自 2026-09-18 起改由雲端經 FinMind 取得**（同樣是台銀的每日牌價，見下方），
所以現在只剩黃金 3 項要靠家用電腦。證交所與 Yahoo 的 8 項不受影響，雲端排程照常更新。

2026-09-08～09-10 又用 `probe-bot` 從雲端量了 12 次、60 個樣本，60 個全部被擋——
這不是偶發，雲端就是抓不到台銀（結果表見下方設計筆記）。

### 解法：家用電腦負責補抓（已設定好）

家用電腦上有四個 Windows 排程工作，都會執行 `scripts/update_local.ps1`：
抓資料 → 有變動就 commit → 推回 GitHub。

| 工作名稱 | 什麼時候 | 做什麼 |
|---|---|---|
| `InvestWatch-Morning` | 每天 10:05 | **完整更新**台銀黃金 3 項（含歷史） |
| `InvestWatch-Midday` | 每天 13:05 | 同上 |
| `InvestWatch-Close` | 每天 15:05 | 同上 |
| `InvestWatch-UpdateLight` | **平日** 09:00–17:00 **每 30 分鐘** | **輕量更新**：只更新黃金存摺的現價，不重抓歷史；實體條塊跳過 |

（2026-09-18 依實際設定重寫。本機**不產報告**，報告只有雲端會產；三個完整更新工作的參數裡還留著
`-Slot morning` 之類的字樣，腳本只記一行 log、不採用——時段標籤只由雲端決定。
這張表就是 `data/schedule.json` 裡 `local` 那一段的來源，改 Windows 工作時兩邊要一起改。）

四個工作都開了「錯過就補跑」。筆電晚上才醒來時，錯過的工作會立刻一起補跑（互斥鎖只讓一個真的跑），
UpdateLight 補跑後有時還會每 30 分鐘連跑幾個小時、有時不會——所以 log 裡看到排程時間以外的執行是正常的，
那是補跑，不是排程。`schedule.json` 記的是**設定的排程**，要核對的話用這一行查實際設定：

```powershell
Get-ScheduledTask -TaskName "InvestWatch-*" | ForEach-Object { $_.TaskName; $_.Triggers | Select-Object StartBoundary,DaysOfWeek,@{n='Interval';e={$_.Repetition.Interval}},@{n='Duration';e={$_.Repetition.Duration}}; $_.Settings | Select-Object StartWhenAvailable,MultipleInstances }
```

`DaysOfWeek=62` 就是週一到週五；`Interval=PT30M`、`Duration=PT8H` 就是每 30 分鐘、持續 8 小時。

> 為什麼完整更新要拆成三個工作、而且各自帶 `--slot`？
> 2026-09-01 踩到：原本三個時段共用一個工作、由程式依當下時間猜時段。
> 10:05 那次因為筆電在待機沒跑到，等 12:10 醒來補跑時已經被猜成「午盤」，
> **整份晨報就永遠消失了**。現在每個時段各自一個工作、帶明確的 `--slot`，
> 補跑再晚也還是寫成正確的時段。

加上雲端，整體分工是：

| 誰 | 什麼時候 | 負責哪些 | 要開電腦？ |
|---|---|---|---|
| 雲端（cron-job.org 觸發 GitHub Actions） | 平日 08:10～17:40 每 30 分；09:30／11:30／13:35／15:30 完整更新＋報告；週末每 2 小時 | 台股 4 項、海外 4 項、匯率 2 項（匯率一天一筆，只在完整更新抓） | ❌ 不用 |
| 這台電腦（完整） | 每天 10:05 / 13:05 / 15:05 | 台銀黃金 3 項（含歷史） | ✅ 要 |
| 這台電腦（輕量） | 平日 09:00–17:00 每 30 分 | 黃金存摺現價（實體條塊跳過） | ✅ 要 |

> 這張表 2026-09-18 重寫過。雲端從 2026-09-09 起不再靠 GitHub 自己的 cron（它從來不準時），
> 改由 cron-job.org 準時觸發，見下方「排程在哪裡」；報告只有雲端會產。
> 誰負責哪幾項的唯一依據是 `data/assets.json` 的 `owner`。

**⚠ 待機時不會跑（2026-09-01 實測）。**
所有工作都設了「喚醒電腦執行」（`WakeToRun`），但這台筆電是**現代待機（S0）**機種——
Windows 在現代待機期間會暫停一般桌面程式，而 `WakeToRun` 是為舊式 S3 睡眠設計的。
實際結果是**一次都沒有把電腦叫醒過**（`powercfg /lastwake` 的喚醒記錄計數為 0）。

2026-09-01 整天只跑了 3 次（09:04、12:10、17:52），全部是**電腦醒來後的補跑**
（`StartWhenAvailable`）。想要真的每 30 分鐘更新，必須讓筆電插電時不要進入待機：

```powershell
powercfg /change standby-timeout-ac 0
```

（`0` = 插電時永不待機；想改回來就把 `0` 換成分鐘數，原本是 `5`。
這只影響插電時，用電池時仍會照常待機省電。）

#### 輕量更新省在哪

| | 完整更新 | 輕量更新 |
|---|---|---|
| 請求數（2026-09-01 量的，當時本機抓全部 12 項） | 14 次 | **9～10 次** |
| 耗時 | 約 25 秒 | **約 13～15 秒** |
| 倉庫變動 | 約 237 行 | **約 44 行** |

省下來的主要是兩份「一年份黃金走勢表」（各約 200KB）。盤中要的是**今天的牌價**，
而台銀黃金主頁（85KB）就同時有牌價和掛牌時間，不必重抓整年歷史。
實體條塊一天大致只設定一次牌價，輕量更新會直接跳過並標明「沿用上次結果」。

> 實測發現：黃金主頁的牌價比歷史走勢表更即時。2026-08-31 23:23 主頁顯示 19:45 掛牌的
> 4,562，走勢表今天那一列還停在 4,558。所以現價一律以主頁為準。
>
> 另外，**存摺和實體條塊的「掛牌時間」是兩回事**：同一時刻實測存摺是 19:45、
> 條塊是 14:54。存摺一路更新到晚上，條塊大致在營業時間內設定一次，
> 所以兩張卡片顯示各自的掛牌時間。

**查看／管理排程**（PowerShell）：

```powershell
Get-ScheduledTask -TaskName "InvestWatch-*" | Get-ScheduledTaskInfo
```

想立刻更新一次：

```powershell
Start-ScheduledTask -TaskName "InvestWatch-UpdateLight"
```

覺得太密集，想改成每小時一次：

```powershell
$t = Get-ScheduledTask -TaskName "InvestWatch-UpdateLight"; $t.Triggers[0].Repetition.Interval = "PT1H"; Set-ScheduledTask -InputObject $t
```

不想要了就全部移除（本機更新就完全停掉）：

```powershell
Get-ScheduledTask -TaskName "InvestWatch-*" | Unregister-ScheduledTask -Confirm:$false
```

執行紀錄在 `scripts/update_local.log`（不進倉庫）。

> 沒有測到雲端環境。
>

> 混淆過的 JavaScript），連在家用電腦上都拿不到資料，比台銀更嚴。玉山銀行的匯率
> 頁面倒是能直接解析，若未來想讓匯率也能在雲端更新，那是可行的方向——但那會變成
> 看玉山的牌價，不是台銀的。
>
> **2026-09-18 更新**：匯率不用換銀行了。FinMind 的 `TaiwanExchangeRate` 轉載的就是台銀的
> 每日牌價（切換前逐日比對 136 天，即期買入／賣出完全一致），而且雲端抓得到，
> 所以這 2 項已經搬到雲端。代價是一天只有一筆、沒有盤中價。見 `docs/CHANGELOG.md` 8-0。

## 個人資料放在哪裡（Phase 3）

「我的紀錄」裡的持倉、成本、金額**永遠不會進入這個公開倉庫**。它們只會在兩個地方：

1. **你正在用的那台裝置的瀏覽器**（localStorage）——不設定任何金鑰就能用
2. **你自己的私人倉庫**（預設 `DAVIDJJX/invest-data` 的 `portfolio.json`）——
   只有在設定頁貼上金鑰、開啟同步之後才會用到

同步金鑰（fine-grained PAT）只存在該台裝置的瀏覽器，畫面上一律遮罩顯示，隨時可清除。
它只需要對那一個私人倉庫有 Contents 的讀寫權限，其他什麼都不能動。

### 為什麼不做「Gmail 登入」

這是純前端的靜態網站，沒有後端可以驗證身分。做一個登入畫面只是把畫面遮起來，
任何人打開瀏覽器的開發者工具就能直接讀出 localStorage 裡的資料——**那是假的保護**，
只會讓人以為安全。

真正有效的是**把資料加密**，所以做的是密碼鎖：啟用後，寫進這台裝置的紀錄與同步金鑰
都會先用你的密碼加密（PBKDF2-SHA256 推導 25 萬次 + AES-GCM 256），
沒有密碼就只是一團亂碼。密碼本身不會被存下來。

⚠ 忘記密碼＝這台裝置上的資料就解不開了（這正是加密該有的行為）。
啟用前請先匯出備份；有開雲端同步的話，私人倉庫那一份還在。

倉庫裡另外設了幾道保險絲（`.gitignore`）：`portfolio*.json`、`*.pat`、`.env` 等
一律不可能被 commit 進來，就算不小心在專案資料夾裡產生了也一樣。

## 資料壞掉的時候會怎樣

這是刻意設計過的（誠實原則）：

- 某個來源抓失敗 → **保留舊的歷史檔不動**，在 `latest.json` 把該標的標成
  `status: "error"` 並記下錯誤訊息與失敗時間。
- 網頁上該張卡片會顯示紅框 **「⚠ 這一項資料更新失敗」＋ 失敗時間**，
  舊價格只會出現在標明「上次成功」的灰字裡，**不會冒充成現價**。
- 其他標的照常顯示，整個網站不會因為一個來源壞掉就掛掉。

### 卡片會自己說「這是舊資料」

抓失敗是一回事；**沒失敗、但該更新的時候沒更新**（筆電睡著了）是另一回事，以前卡片上完全看不出來。
現在每張卡片依 `latest.json` 裡後端算好的 `freshness` 掛標示（規則在 `js/freshness.js`，只有呈現、不重算新舊）：

| 情況 | 卡片上看到 |
|---|---|
| `freshness = stale`（排定的更新沒有跑到） | **黃色**：「沿用 09-13 23:21 的資料（牌價日期 2026-09-11）——排定的更新沒有跑到」 |
| `freshness = error`（從來沒有成功紀錄，或排程設定缺了這一邊） | **紅色**，而且**不顯示價格與買賣價**——不知道新舊的數字不該被當成現價 |
| `status = error`（這一輪抓失敗） | 原本就有的紅框、「更新失敗」、上次成功價「僅供參考」；不另外重複掛標示 |
| `carriedOver = true`（這一輪刻意沒重抓：實體條塊與匯率一天只更新一次） | 一行灰色小字「這一輪未更新，沿用上次結果（原因）」——不是警告 |
| 台銀與台股、今天是週六或週日、牌價日期是剛過去的星期五 | **中性灰**：「週末不掛牌／不開盤，沿用週五 … 的牌價」。週五的數字就是現在的牌價，不是舊資料，所以不用黃色；原本那段黃色的「今天還沒有新報價」也不再出現 |

- 資料新不新**只有一套規則**：`scripts/merge_latest.py` 依 `data/schedule.json` 比「上一個排定的更新時間」，
  不是比「距今多久」（實體條塊一天只前進三次，用「幾小時內算新」會天天誤判）。前端照 `freshness` 顯示，不自己再算一次。
- 週末的判斷看的是**牌價自己的日期**，不是最後抓取的時間：筆電週日晚上才醒來抓，抓到的還是週五的牌價。
  星期幾一律用台北時間算，不看瀏覽器所在的時區。
- **已知限制**：只認得週六、週日。平日的國定假日沒有假日表，卡片照樣會黃——那是多提醒一次，不是說謊。
- 想看週末的樣子不用等到週末、更不要去改電腦的時間：網址後面加 `?now=2026-09-19T10:00:00+08:00`，
  頁面上方會出現紅色的「示範模式」字樣，資料本身一個字都不會變。
- 筆電白天睡著時，黃金那 3 張卡片在平日白天會**常態性地**出現黃色。那是實話，不是故障；
  要它不黃，得讓資料真的更新（下一階段的估算序列，或一台不會睡的機器）。

### 回滾一次上線

`main` 已經推上去了，所以**不要用 `git reset`**（那會弄亂已經公開的歷史）。
用 `revert` 把整個 merge 反轉成一筆新的 commit：

```bash
git revert -m 1 <merge commit 的編號>
git push
```

`-m 1` 的意思是「回到 merge 之前 main 那一邊的狀態」。
編號可以用 `git log --oneline --merges -5` 找。

### 排錯：某天起每天固定某個時段，雲端那幾項資料全部標示過期

**代表 GitHub Actions 的觸發時間漂移了**，不是資料真的壞掉。
`data/schedule.json` 裡 `cloud.full.at` 寫的是「雲端資料實際到貨的時間」，
那個值是量出來的，不是照 cron 填的（原因寫在該檔案的註解裡）。

處理步驟：

```bash
# 1. 重新量最近 5 天排程實際觸發的時間（UTC 原值）
gh api "repos/DAVIDJJX/invest-watch/actions/workflows/update-data.yml/runs?per_page=15"   --jq '.workflow_runs[] | select(.event=="schedule") | .created_at'
```

2. 把每個時間 +8 小時換成台北時間，看它們分成幾群。
3. 每一群算出可以宣告的區間：
   `最晚到貨時間 <= 宣告時間 <= 最早到貨時間 + graceMinutes`
4. 區間有效的那幾群，把宣告時間填進 `cloud.full.at`；
   **區間是空的（那一群的跨距大於寬限）就不要填那一群** —— 填了一定會有某幾天誤報。
5. 改完把日期與量測結果一併寫進 `data/schedule.json` 的註解，再跑一次
   `python -m unittest discover -s scripts -p "test_*.py"`。

⚠ **不要用放寬 `graceMinutes` 的方式解決。** 那是在調參數追一個會漂移的外部排程，
下次漂了不會有人知道要再調，只會看到網站又開始亂報。

## 設計筆記：之後可能要改的方向（尚未實作）

### 雲端與家用電腦的排程性質不同，應該用不同的模型

- **家用電腦**跑在 Windows 工作排程器上，時間可信 → 用「上一個排定時間」判斷過期很準。
- **雲端**跑在 GitHub 的共用排程上，時間會漂、還會漏跑 → 對它宣告固定的時鐘時間，
  這個模型本身就是錯的（2026-09-05 實測：cron 宣告的三個時間點沒有一次準時發生）。

比較誠實的做法是讓 `data/schedule.json` 每個 owner 選一種模型：

```jsonc
"local": { "full": { "at": ["10:05", "13:05", "15:05"] } },   // 維持現狀
"cloud": { "maxAgeHours": 20 }                                 // 上次成功超過 20 小時才算過期
```

這**不是**回到停點 2 砍掉的 `freshnessMinutes`。那條被砍，是因為實體金條塊的更新節奏
是「設計上」一天三次，用「距今多久」一定會誤判；而雲端的不規律是「外部系統的不確定性」，
年齡門檻正好是為這種情況存在的。兩者的成因不同，適用的模型也不同。

### 黃金 3 項的去向（2026-09-18 的決定）

存摺組與條塊組都不通過，所以**黃金存摺 TWD、黃金存摺 CNY、實體條塊留在家用電腦**（`owner=local` 不動）。

- 這一輪只把筆電這條路修到「醒著就一定會成功」：同時啟動的多個實例不再互撞（互斥鎖）、
  倉庫裡出現不相干的未追蹤檔案不再讓整條管線中止（見維運區與 `docs/CHANGELOG.md` 8-3）。
  筆電睡著的時候黃金還是不會更新——卡片會自己說那是舊資料（8-4）。
- 下一階段（8-B，另案）：雲端用國際金價換算一條**估算序列**當保底，台銀官方牌價仍由筆電抓，
  兩者分開標示，估算的永遠不冒充官方牌價。本停點不做。
- 如果哪天要把「直接抓台銀」搬上雲（台銀放寬防護，或改用一台不會睡的家用機器），規格得先補這幾件事，
  現在的程式都沒有：
  1. 「連續 N 次被擋就退避、恢復後自動繼續」需要**跨輪**的計數。現在的 `Fetcher.blocked` 只活在單次執行裡。
  2. 「沿用上次成功值」只能用 `status=error`＋`lastGood` 呈現（卡片印「上次成功、僅供參考」），
     **絕不可以把舊價寫回 `price`**——那就是拿舊資料冒充新資料。
  3. 黃金存摺 CNY 在輕量更新仍然會抓半年走勢表（黃金主頁只解析得到台幣那張表），不符合「輕量只抓現價頁」。
  4. 請求量：平日每 30 分一次輕量更新，對台銀的請求會是 probe 量測頻率的數倍；
     probe 量的是「會不會被直接擋」，通過也不代表不會被限流。

### 對台銀的請求要克制

臺灣銀行有機器人防護。雲端的資料中心 IP 就是這樣被擋掉的（所以直接抓台銀的那幾項才要由家用
電腦補抓），而且用 `curl` 直接抓也會拿到驗證頁——本專案的 `Fetcher` 帶了正確的
標頭才過得去。**一旦連家用電腦也被擋，本機負責的黃金 3 項會整個失效**，那是這個
專案最脆弱的一環。

因此：

- **盤中的輕量更新（平日每 30 分鐘）只抓「現價」需要的東西，不抓歷史檔。**
  實測請求數：匯率還在本機時，完整更新 8 次、輕量更新 4 次；2026-09-18 匯率搬到雲端之後，
  本機完整更新實測 5 次（少掉當日匯率 CSV 與兩份 L6M 歷史檔）、輕量更新實測 3 次（少掉當日匯率 CSV）。
- 實體黃金條塊在輕量更新直接跳過（一天只掛牌一次，盤中重抓是白費）。
- 新增任何一個對台銀的請求之前，先問：這個請求需要每半小時發一次嗎？
  不需要的話就只放在完整更新裡。
- `scripts/test_history_dates.py` 有兩條測試釘住這件事
  （`TestBankOfTaiwanRequestRestraint`），改壞會紅。

### 歷史檔裡的每一天，都必須是那一天真的存在的報價

`data/history/<id>.json` 的每個點都有 `dateSource`，記錄這一天的日期是從哪裡來的：

| 值 | 意思 |
|---|---|
| `quote` | 台銀網頁上的掛牌時間 |
| `chart` | 台銀黃金走勢表自己的日期欄 |
| `csv` | 台銀匯率 CSV 的資料日期欄（2026-09-11 以前的匯率點） |
| `finmind` | FinMind `TaiwanExchangeRate` 回應自己的 `date` 欄（台銀每日牌價；2026-09-14 起的匯率點） |
| `official` | 證交所官方月檔的日期欄 |
| `realtime` | 證交所即時報價自己回傳的日期 |
| `yahoo` | Yahoo 日線 K 棒自己的時間戳 |

**絕對不可以用「現在」當歷史點的日期。** 台銀週末不掛牌，週六抓到的還是週五那一筆；
用現在當日期就會憑空生出一個週六的點，值跟週五一模一樣，走勢圖上多一根不存在的
K 線（2026-09-05 實際發生過，已修正並清掉 4 筆假點）。

讀不到來源的日期時，**寧可不寫歷史**，並在該項的 `historyNote` 寫明原因。

### 兩件事、兩個機制，不要擠在同一個參數

- **per-asset 的 `freshness`** 管「這個數字新不新」
- **per-source 的 `runAt` 年齡** 管「這台機器還活著嗎」

「雲端停擺最慢隔天 15:20 才發現」這個空窗，補法是後者（watchdog 直接看
`sources.<owner>.runAt` 的年齡，超過 N 小時就開 Issue），不是放寬前者的寬限。
